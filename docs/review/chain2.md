# Adversarial re-review of programs/heartrot after the archer/class-byte slice (working tree over 6fc72d5)

## Verdict

ALL CLEAR on the chain half. I found no defect I can demonstrate with a concrete failing input. Every hunt target the brief named came back negative, and most came back negative with a number I re-measured rather than an argument I read.

Scope of the delta, verified: `lib.rs` is unmodified, so there are NO new instructions and nothing new that could be missing a signer/owner/PDA check. The entire on-chain change is (a) `PlayerSlot._pad0` -> `class_aim` at offset 3, (b) `JOIN_DATA_LEN` 66 -> 67 with `class` at `data[66]`, (c) `SHOT_DAMAGE`/`SHOT_COOLDOWN_TICKS` becoming `CLASS_DAMAGE[class]`/`CLASS_COOLDOWN_TICKS[class]` in `shoot::fire`, and (d) two new consts + const-asserts in the generated `map.rs`. Everything else in the Rust diff is rustfmt and doc.

Gates, all run: `cargo check --workspace` 0. `cargo test -p heartrot` unit line **104 passed** (doc-test line reads 0 passed / 1 ignored and is not the line) — the spec's gate was >=97. `HEARTROT_TREASURY=FbDoanj... cargo build-sbf` 0. `(cd app && npx tsc --noEmit)` 0, `(cd packages/client && npx tsc --noEmit)` 0, `(cd worker && npx tsc --noEmit)` 0.

THE CLASS BYTE IS UNTRUSTED INPUT AND IT IS HANDLED. A class of 200 is refused twice, never clamped: `parse_join` (`programs/heartrot/src/handlers/player.rs:531-540`) rejects `class >= N_CLASSES` with `InvalidInstructionData` before any account is borrowed, and `PlayerSlot::set_class` (`state.rs:1000-1007`) refuses again as the encoder. The alias cases are covered too — `a_join_carries_a_class_and_refuses_an_unknown_one` sweeps `N_CLASSES`, `N_CLASSES+1`, `CLASS_MASK`, `CLASS_MASK|1`, `u8::MAX` and asserts a refused class writes nothing. More importantly the read side cannot fault at all: `class()` is `class_aim >> 7` on a `u8`, which is total, so `CLASS_DAMAGE[..]` and `CLASS_COOLDOWN_TICKS[..]` (both len 2) have no reachable panic branch no matter what byte a corrupt account holds. And `join` is treasury-signed anyway (`validate_pair(..., treasury_ai, true)` plus `treasury_key == arena.crank_authority`), so a browser never reaches this byte directly.

PlayerSlot IS STILL 96 BYTES AND CLASS 0 IS STILL THE KNIGHT — confirmed at runtime against the shipping ELF's own fixtures, not just from the const block: `LAYOUT PlayerSlot 96 B, Players 1924 B, Arena 1200 B, Boss 50 B, LAYOUT_VERSION 1`. Rent-exempt minima are unchanged (Arena 9,242,880 / Boss 1,238,880 / Players 14,281,920 lamports), so the 0-lamport migration claim holds. `offset_of!(PlayerSlot, class_aim) == 3` is const-asserted between `skin_id` at 2 and `x` at 4. `a_zeroed_seat_is_the_knight_it_already_was` proves a zeroed slot yields 40 damage and `ticks_for(800)-1` cooldown — the shipped knight. And every seat any version of this program ever wrote has 0 there: `claim_seat` is `*slot = PlayerSlot { .., ..PlayerSlot::zeroed() }` and `Players::reset_for_incarnation` is `[PlayerSlot::zeroed(); MAX_SEATS]`, so byte 3 is never left inherited.

NO HARD FREEZE EXISTS, and I re-derived this rather than trusting the tests. Replaying the real move rule (`!is_wall(nx,ny) && may_move_to(zone, y, ny)`) over the shipped `map::WALLS`:
  - BFS from all 20 `entrance_for(seat)` under ZONE_ARENA: 92,928 reachable positions, **0** with no legal step.
  - BFS from all 20 `lobby_spawn(seat)` under ZONE_LOBBY: 170,240 reachable positions, **0** with no legal step. That 170,240 is the exact figure `player.rs`'s own comment records — an independent confirmation of the lobby box.
  - Walls alone, over all 1,048,576 unit positions: **0** floor positions have no non-wall 8-neighbour. This is what makes `may_move_to`'s un-stranding clause ("a stranded seat is governed by walls ALONE") safe — it cannot hand a stale-account seat a position with nothing to do.
I also chased the one gap I thought I had found — that `entrance_for`'s fanned ranks (offset +/-48 off the four `E` marks) might not be proven floor, since `map.rs:207-221` only sweeps `ENTRANCES` itself. It IS proven: `tick.rs:958-969` is a `const _: () = {}` that walks all `MAX_SEATS` fanned points and asserts `!wall_at`, `player.rs:1201-1206` asserts every one is inside the arena box, and `player.rs:1318-1325` asserts every one has a legal step in all three playable phases. I verified the 20 positions by hand: x in {160,352,672,864}, y in 464..560, all floor, all inside PIT_TOP 384..PIT_BOT 607. Retracted.

THE BOSS CANNOT BE MADE UNKILLABLE BY THE ARCHER, measured on the current ELF with `scripts/spike/cu-archer` (mollusk-svm 0.15.1, ARENA_SEED=1): 1,200-tick fight mix with 20 seats firing at class cadence gives **peak live bullets 23 of MAX_BULLETS 128** for knights AND for archers — no player projectile enters the swept-collision loop, exactly as designed. `boss_tick` at 20 seats pinned is **max 22,192 CU of 399,700 (5.55%, 18.0x headroom)** and is byte-identical between the knight and archer mixes. `shoot` CU is identical per class (5,255 point-blank / 7,575 at 120u / 9,910 at 200u / 14,083 full 64-step miss), so the class lookup costs nothing the instrument can see. Bullet slope 716-839 CU per live projectile per tick, confirming the ~718 figure the on-chain-arrow rejection was based on.

DPS NEUTRALITY IS REAL ON CHAIN, not just in the const block: the same harness accepted **3,000 knight shots vs 1,700 archer shots over the same 1,200 ticks** (ratio 1.765 against the table's 14/8 = 1.75), every accepted shot damaging the shell. The boss needs no rescale.

A FIGHT CAN ALWAYS END. `end_fight` is total and idempotent (refuses `OUTCOME_UNDECIDED`, refuses `outcome > OUTCOME_ENRAGE`, refuses a non-FIGHTING phase, refuses an already-written outcome), `enrage_at_tick` forces `OUTCOME_ENRAGE` at 6 min, and the difficulty curve is self-limiting: `begin_roll` requires `outcome == OUTCOME_WIN`, so a raid that stops winning stops advancing the incarnation and `scale_for_incarnation`'s u16 saturation can never be reached by losing.

ARITHMETIC: `set_aim` uses `unsigned_abs` (so `i8::MIN` is safe) with u32 intermediates peaking at 128*15+64 = 1,984, and its ratio is provably <= 15, so `(sector << 4) | ratio` can never touch bit 7 — the shipped sweep proves this over all 65,535 legal wire aims at 1.90 deg worst reconstruction. `octant` and `unit_q12` both widen to i32 before `abs`. `recompute_vent` uses `saturating_mul` on u32 whose true maxima (58,981,500 and 20,643,525) never approach saturation. The only writes to `boss.x`/`boss.y` outside `init` are inside `#[cfg(test)]`, so `raycast`'s `core_dx*core_dx + core_dy*core_dy` stays four orders inside i32.

The `& CLASS_MASK` silent-failure the spec singled out has its dedicated test on BOTH sides — `state::class_tests::an_aim_write_never_changes_the_class` and `shoot::tests::the_class_bit_survives_every_shot` (20 shots, archer keeps bit 7 and scores 70 each). Both pass.

## Good

- PlayerSlot is still 96 bytes and class 0 is still the knight — confirmed at runtime from the shipping ELF's fixtures (`LAYOUT PlayerSlot 96 B, Players 1924 B, Arena 1200 B, Boss 50 B, LAYOUT_VERSION 1`), not merely from the const block. Rent-exempt minima unchanged, so the 0-lamport / no-migration claim holds.
- The class byte is refused, never clamped, at both the wire (`parse_join`, before any account borrow) and the encoder (`set_class`) — including the values that would alias onto a legal class if the byte were masked (CLASS_MASK, CLASS_MASK|1, u8::MAX). And the read path cannot fault at all: `class_aim >> 7` on a u8 is total, so both class-table lookups have no reachable panic branch for ANY byte value, including on a corrupted account.
- No new instructions at all — lib.rs is unmodified — so there is nothing new that could be missing an owner, signer or PDA check. The existing perimeter on `shoot` is intact: assert_signer, assert_owned_by + assert_writable on all three accounts, assert_pda_at_bump binding Boss and Players to the arena key, phase gate, `get_mut` seat bound, then assert_session_authority. `join` still requires the treasury signature AND `treasury == arena.crank_authority`.
- Zero legal moves is unreachable, re-measured independently against the shipped WALLS: 92,928 arena positions reachable from the 20 entrances with 0 frozen; 170,240 lobby positions from the 20 spawns with 0 frozen (matching player.rs's own recorded 170,240); and 0 of all 1,048,576 unit positions on the whole map have no non-wall 8-neighbour, which is what makes the stranded-seat escape clause safe for accounts the old program wrote.
- The entrance fan is fully guarded, which is easy to miss: `tick.rs:958` const-asserts all 20 fanned respawn points are floor, `player.rs:1201` asserts each is inside the arena box, and `player.rs:1318` asserts each has a legal step in every playable phase. I verified the 20 positions by hand (x in {160,352,672,864}, y 464..560, all floor, all inside PIT_TOP 384..PIT_BOT 607). This is the exact defect class the brief called most dangerous, and it is closed.
- The archer allocates nothing and costs nothing measurable: 1,200-tick fight mix with 20 archers firing peaks at 23 live bullets of 128 — identical to 20 knights — and `boss_tick` max is 22,192 CU of 399,700 (5.55%), byte-identical across both mixes. `shoot` CU is identical per class at every range (5,255 / 7,575 / 9,910 / 14,083). The ER speed the user protected is untouched on the chain side.
- DPS neutrality is demonstrated behaviourally, not just asserted: 3,000 knight shots vs 1,700 archer shots accepted over the same 1,200 ticks (1.765 vs the table's 1.75). The boss's HP curve needs no rescale, which is what makes this a zero-migration balance change.
- The state machine cannot wedge a live raid. `end_fight` is total and idempotent on all four of its refusal conditions, the enrage clock forces an outcome at 6 minutes, and MUSTERING/FIGHTING/ROLLING all have a `crank_authority`-gated escape to SETTLED so a dead crank cannot strand three delegated accounts in a phase with no exit. The difficulty curve is self-limiting because only a WIN advances the incarnation.
- Arithmetic is clean on every path the new byte touches: `set_aim` uses `unsigned_abs` with u32 intermediates and a ratio provably <= 15 (so bit 7 is untouchable), `octant` and `unit_q12` both widen to i32 before `abs` so `i8::MIN` from the wire is safe, `recompute_vent` saturates on values that never approach saturation, and boss position is written only by `init` so `raycast`'s squared-distance stays four orders inside i32.
- The spec's named single point of silent failure — dropping `& CLASS_MASK` in the aim write — has a dedicated test on both sides (`an_aim_write_never_changes_the_class` and `the_class_bit_survives_every_shot`), and the write itself lives in state.rs beside the field rather than inlined at the call site, so there is exactly one line to get right.
- The client gates the trigger on the CHAIN's class, not the local selection: App.tsx:402 passes `classOf(slot)` into `shotAllowed`, and `Hud.tsx:96`'s hardcoded `SHOT_COOLDOWN_TICKS = 1` is gone with `shotAllowed` exported from controls.ts. That was Correction B in the spec and it is the half of 'the space bar doesn't work' that was a live-fight bug, not a lobby one.

## Still open

- docs/perf/chain-cost-archer.md section 0 names a TREE binary that is no longer on disk. Its provenance row records 116,360 B / sha256 548e004f...; `HEARTROT_TREASURY=FbDoanjAUonn5wM4KbRNS3jigHe6zDa4ThoEUKPnS7ka cargo build-sbf` on the current tree produces 116,416 B / sha256 a155707b123d03f3893bb72d7dac1a1fe88d574361ef760836670748fde9d215 (the 56-byte delta is consistent with map.rs's newly added const-assert panic strings). I re-ran the harness against the ELF that is actually there and every headline number in that document reproduces exactly, so the measurements are sound — only the binary the table names is not the shipping one. Repo rule is 'never claim a measurement you did not run'; update the row. Low, doc-only.
- A lost arena is terminal and its rent is unrecoverable, which is the mechanism behind the treasury drain in spec section 13. PHASE_EDGES has SETTLED -> LOBBY as the only way back, `begin_next_incarnation` requires `next_affix_seed != 0`, only `consume_roll` writes that, and it is reachable only through SETTLING -> ROLLING which `begin_roll` gates on `outcome == OUTCOME_WIN`. So a wipe or an enrage retires the arena permanently: 9,242,880 + 1,238,880 + 14,281,920 = 24,763,680 lamports (0.0248 SOL) per lost raid, plus ER top-up. It is documented in the edge table so it is a design decision, not a defect — but the drain scales with LOSSES, not with runs, and nothing in the program reclaims it. Worth naming before the next perf sitting.
- The archer's class is fixed for the incarnation and there is no wire signal saying so. `join`'s returning-identity branch (player.rs:608-625) rotates `session_pubkey` and `skin_id` but deliberately not `class`, and returns Ok(()). A Worker sending classId 1 for an identity already seated as a knight gets a success with the class silently unchanged. The client is correct today — App.tsx:402 derives `cls` from `classOf(slot)`, so the cooldown gate follows the chain, not the local selection — and that single line is the only thing standing between a re-select and a fresh 'the space bar doesn't work' report. Not a defect; it is the line to protect in review. The `ponytail:` comment already names the upgrade path (gate a rotation on `last_shot_tick == 0`).
- Deploy order remains an indivisible three-way (program + app + worker), by design. The devnet ELF is confirmed pre-archer by behaviour — it accepts the 66-byte join block and refuses the 67-byte one — and my run confirms the tree does the exact opposite (66 bytes -> InvalidInstructionData at 126 CU, 67 bytes -> Ok at 2,314 CU). Ship the app or the worker first and every join fails. Already stated in the spec; still open as an operational hazard, not a code one.
- `cargo build-sbf` fails without HEARTROT_TREASURY (init.rs:134 const-asserts it, behind cfg(target_os="solana")) while `cargo check --workspace` passes. Anyone gating CI on cargo check alone will not notice a broken deploy build. Pre-existing.
- Unchanged pre-existing ceilings I re-confirmed rather than re-litigated: props are not solid (R4 needs a map edit + gen_map.py), two classes is the aim byte's budget (a third costs 4.05 deg and a 62-unit p95 miss), and `shoot` write-to-visible has still never been measured at any seat count — the 129.8 ms baseline is a `move` measurement over a read-only Arena, and `shoot` takes Arena + Boss + Players all writable. Any future cooldown change is still a guess against the user's hard constraint until that measurement exists.
