# chain-correctness: adversarial review of programs/heartrot (native Pinocchio)

## Findings

Baseline is clean: `cargo test -p heartrot` reads `running 85 tests` / `85 passed`, `cargo check --workspace` exits 0 (4 pre-existing `unexpected_cfgs` warnings). The perimeter itself is solid — every handler owner-checks, signer-checks and re-derives the boss/players PDA from the arena address, `load*` gates discriminator + version, seat indices all come off `slots.get_mut(..)`, and I could not find an arithmetic path that overflows under `overflow-checks = true`. Seven defects, ranked. Fix 1 and 2 before the next devnet deploy; 3–5 are one-liners.

**1. HIGH — `PHASE_ROLLING` has no operator exit; a dead crank strands three delegated accounts forever.** `Arena::abandon_roll` (state.rs:656) is the only `ROLLING → SETTLING` writer and is called from exactly one place: `tick::heartbeat` (tick.rs:429). `PHASE_EDGES` (state.rs:514) has no `(ROLLING, SETTLED)`, so `settle` tag 9 (settle.rs:421, via `try_set_phase`), `process_commit` tag 11 and `process_commit_and_undelegate` tag 12 (delegation.rs:459, explicit `if a.phase == PHASE_ROLLING { return Err(WrongPhase) }`) all refuse. Concrete input: raid wins → `fire` stamps `OUTCOME_WIN`/SETTLING (shoot.rs:416) → `request_roll` → ROLLING; the crank task is deleted inside the ~10 s roll window (the docs' own open risk R5: a tick over 399,700 CU ten times deletes the task permanently) and the VRF request expires unfulfilled. `arena.tick` now never advances, so `abandon_roll`'s own timeout `tick - roll_requested_tick > ROLL_TIMEOUT_TICKS` can never elapse either — and nothing calls it anyway. Arena/Boss/Players stay delegated to the ER with **no instruction in the program able to undelegate them**. Fix: let tag 12 (already treasury/`crank_authority`-gated) force ROLLING → SETTLED. The hazard it was excluded for — a VRF callback landing on an undelegated account — costs the oracle retries bounded by the request's 240-slot TTL, strictly cheaper than a permanently stranded match. `FIGHTING → SETTLED` exists for exactly this reason; ROLLING is missing its twin.

**2. MEDIUM — a `ZONE_LOBBY` seat can walk the entire map, including inside the boss's head.** `player::in_arena_box` (player.rs:232) is `zone != ZONE_ARENA || (PIT_TOP..=PIT_BOT).contains(&y)` — the clamp applies *only* to raiders. Gate rows 38/39 and the doorway rows 36/37 are floor, and rows 1..23 are deliberately floor ("boss air", so `raycast` is not killed by a wall). BFS over the shipped `map::WALLS` with the shipped 8-way `MOVE_STEP`, from lobby spawn (448, 832): a lobby seat reaches 445,696 distinct positions, minimum y = **16** — tile row 1, inside `crown` (boss-local y −384..−207 → world 16..193). An arena seat from entrance (512,512) is correctly held at min y = 384. The bypassing seat is invisible to every mechanic (not in `live`, never targeted by `spawn_volley`, unslammable, cannot shoot) but every client renders it standing in the creature. The gate is supposed to be the commitment; for movement it is optional. Fix is one line: give the non-arena branch `y > PIT_BOT`. `enter_gate` teleports to `entrance_for(seat)` (player.rs:694), so no lobby seat ever legitimately needs to be above the rim.

**3. MEDIUM — `HeartrotError::MatchNotRecorded` (17) is declared, documented, and never constructed.** `grep -rn MatchNotRecorded programs/` returns only error.rs:45, :217 and the docstring at :205-216 — which spells out precisely why the code exists ("this is the retryable one: send tag 10, then tag 15 again... Not `WrongPhase`: the arena's phase is exactly right, and the stale account is the *Leaderboard*"). init.rs:735 returns `HeartrotError::WrongPhase` instead. Concrete input: settle a won+rolled match to SETTLED, send tag 15 (`next_incarnation`) before tag 10 (`write_leaderboard`) → custom error **6** on an arena whose phase is correct. On the ER the error code is the only diagnostic a failed transaction returns, and guards.rs's stated "distinct errors" contract is the thing being violated.

**4. LOW/MEDIUM — the opening volley of every fight has no wind-up.** `Boss::reset_for_incarnation` sets `attack_timer = 0` (state.rs:782) with the comment "the first attack beat is the crank's to schedule", but `tick::step` reads `attack_timer == 0` as *fire now* (tick.rs:816-822). So the first FIGHTING tick both publishes `boss.target_seat` for the first time and spawns `3 + alive_count` aimed bullets in the same write. `volleyTelegraph` (app/src/render/Arena.tsx:215) returns null while `arena.phase !== PHASE_FIGHTING`, so no client can ever draw that wind-up; every later volley gets the full 32 ticks. This is invisible to the suite because the `fight()` fixture (tick.rs:1185) hand-sets `attack_timer = VOLLEY_INTERVAL_TICKS` rather than calling `reset_for_incarnation`. Fix: move `VOLLEY_INTERVAL_TICKS` beside the other `ticks_for` constants in state.rs and seed `attack_timer` from it.

**5. LOW — `init_arena` accepts a `crank_authority != TREASURY` and silently makes the arena a one-shot.** init.rs:491 only rejects all-zero. But `write_leaderboard` requires the payer to be BOTH `TREASURY` (settle.rs:486) and `arena.crank_authority` (settle.rs:503), while `join` (player.rs:486) only requires `crank_authority`. Concrete input: `init_arena(arena_id=1, crank_authority=<any key ≠ treasury>)` succeeds; the arena delegates, musters, fights and settles normally, then `write_leaderboard` returns `NotTreasury` forever, so `next_incarnation`'s leaderboard check (init.rs:734) never passes. One line at init: reject `crank_authority != TREASURY`, or drop the redundant `TREASURY` test in `write_leaderboard`.

**6. LOW — any non-WIN outcome terminates the arena permanently.** Intended and unit-tested (state.rs:1249), but restating the reachable input: `OUTCOME_ENRAGE` is the 6-minute timeout and is reachable whenever a raid is under-manned; it leaves `next_affix_seed == [0;32]`, so `begin_next_incarnation` refuses forever (state.rs:693). The match files correctly and the arena can never host another raid — a fresh `arena_id` is the only recovery. Separately, `OUTCOME_WIPE` is unreachable: tick.rs:859 requires `pending_respawns == 0`, and `damage_seat` (tick.rs:527) unconditionally stamps `respawn_at_tick`. Spec §12.14 cuts that deliberately; confirming it is still true.

**7. LOW — one unchecked index remains on the must-never-panic crank path.** `damage_seat` does `players.slots[live[i].seat as usize]` (tick.rs:521). Safe today (`live` is filled only from `0..MAX_SEATS` at tick.rs:594), but tick.rs's own module docstring claims "no unchecked index", and a panic here burns a crank retry.

**Spec conflict, not a defect:** §4.1 requires "`unit_velocity`: round instead of truncate (5.07° → 2.95°)". tick.rs:346 truncates, and the shipped docstring argues *for* truncation on a different axis (never exceeding `BULLET_SPEED`). Both goals are satisfiable — round the quotient, keep alpha-max-beta-min's over-estimate — but the spec's change was not landed. Flagging per instructions rather than diverging.

**Things I tried to break and could not:** the boss is killable. Replaying `raycast` verbatim (Q12 normalisation, truncating division, `MAX_RAY_STEPS = 64`, first-match-by-index over the generated `PART_HITBOXES`) from all 726 pit/entrance/heart stands against 960 distinct i8 aim pairs: every stand can hit something with a full shell, and 152 stands can already reach the core. Iteratively destroying whatever is reachable strips the shell to **0 residual HP in 2 rounds** — `thorn2` is fully shadowed by `mace` (index 7, world x 170..502 y 301..711) while the mace stands, and opens up the moment it falls, exactly as §5.5 predicts. `shell_max` is 18,000 and the vent needs `< 6,300`, so the vent always opens. Repeating with a *stale* `Boss.y = 320` (an already-live devnet account created before `BOSS_SPAWN` moved) gives the same result: still winnable, 151 core stands. I also chased and cleared the deadlock §1.3 warned about — a player who flips zone standing on gate row 39 is two tile rows below `PIT_BOT`, but `enter_gate` teleports to `entrance_for(seat)` (y ∈ 464..560) before the clamp ever applies, so there is no freeze. Crank iteration budget is fine: `TICK_ITERATIONS = 4,750` against a worst case of 200 muster + 3,600 enrage = 3,800, leaving 950 > `ROLL_TIMEOUT_TICKS` (100). The overlapping-volley pool assert holds with real numbers (lifetime 37, interval 32, 2 volleys × 23 = 46 ≤ 128). The TS mirrors agree: `slamLane`/`slamTelegraph` (packages/client/src/layout.ts:667, :694) correctly use `floor(tick/PERIOD)+1` during the wind-up, which is the cycle-division trap the chain's private `slam_lane` would otherwise hand a client; `shoot` is 4 bytes and `move` 6 on both sides.

## Evidence

Baseline: `cargo test -p heartrot 2>&1 | grep -E "^test result|running [0-9]+ test"` → `running 85 tests` / `test result: ok. 85 passed`. `cargo check --workspace` → 0 (4 pre-existing unexpected_cfgs warnings).

Finding 1: `grep -rn "abandon_roll"` in programs/heartrot/src returns one call site, tick.rs:429. state.rs:514-527 `PHASE_EDGES` has 12 entries, none `(ROLLING, SETTLED)`; state.rs:1157 asserts that absence. delegation.rs:459 refuses ROLLING for both tag 11 and tag 12. settle.rs:421 routes through `try_set_phase`. state.rs:660 `abandon_roll` compares `self.tick.saturating_sub(self.roll_requested_tick)`, and `tick` is only advanced by `heartbeat` (tick.rs:423).

Finding 2: BFS over `map::WALLS` parsed from the generated map.rs, using player.rs's `MOVE_STEP` (±16 cardinal, ±11 diagonal) and `clamp(0, MAP_MAX_XY)`. ZONE_LOBBY from (448,832): 445,696 reachable positions, min y = 16. ZONE_ARENA from (512,512): 92,928 positions, min y = 384. `crown` = `Rect{x:21,y:-384,w:201,h:177}` at `BOSS_SPAWN=(512,400)` → world y 16..193.

Finding 3: `grep -rn "MatchNotRecorded" programs/heartrot/src` → error.rs:45 (doc table), error.rs:217 (declaration), error.rs:205-216 (docstring). No construction site. init.rs:735 is `return Err(HeartrotError::WrongPhase.into());`.

Boss-killability simulation (replays `unit_q12` + `raycast` + `is_wall` against the generated `PART_HITBOXES`/`CORE_*`/`WALLS`, 726 stands × 960 i8 aims): full shell → 726/726 stands hit something, 152 reach core, parts {0,1,3,4,5,6,7,8} reachable, part 2 shadowed by part 7. Strip reachable → part 2 becomes reachable → residual shell 0/18,000. Same run with `BOSS.y = 320`: 151 core stands, residual 0.

Volley pool: `travel = 1536`, `lifetime = ceil(1536/42) = 37`, `VOLLEY_INTERVAL_TICKS = 32`, `volleys_in_flight = 2`, `2 × (3+20) = 46 ≤ 128` — the const-assert at tick.rs:284-288 is sound.

Arithmetic bounds I checked by hand and could not break: `spawn_volley`'s `aim*24 ± aim*k` peaks near 76k (i32-safe); `unit_velocity` output is bounded by `|v|/approx_len ≤ 1` so both casts fit i8; `bullet_hits` peaks around 3.1e10 in i64; `raycast`'s `fx` peaks near 8.4e6 in i32; `arena_occupants.max(1).min(MAX_SEATS) as u16 - 1` cannot underflow; `boss.attack_timer -= 1` and `*live_n -= 1` are both guarded; `board.entries[cursor]` uses `% LEADERBOARD_CAP`; `1u32 << seat` is bounded by `slots.get_mut(seat)` returning None above 19.

## On-chain

Every one of the seven findings is on the chain side, and five of them must stay there.

MUST BE ON CHAIN — twenty clients have to agree, or the fix does nothing:
- Finding 1's new `ROLLING → SETTLED` edge. It decides whether three delegated accounts ever come back to the base layer; only the program can undelegate accounts it owns, and `PHASE_EDGES` is the single place the legality is stated. A Worker-side retry loop cannot substitute — every instruction it could send already refuses.
- Finding 2's clamp. `in_arena_box` gates `move_player`, so it is a movement *rule*, not a drawing. Enforcing it client-side produces the project's signature misdiagnosis in reverse: a legal-looking move the client blocks that the chain would have accepted.
- Finding 4's `attack_timer` seed. `spawn_volley` runs in `tick.rs` and writes `Arena.bullets`; the wind-up length is what the client reads out of published `attack_timer`. Seeding it client-side would make the drawn telegraph disagree with the bullets that actually arrive.
- Finding 5's `crank_authority` check. It decides who may file a result and advance an incarnation.
- Finding 7's index. It is inside the handler that must never `Err` or panic.

CLIENT-VISIBLE BUT NOT CLIENT-FIXABLE: finding 3 is an error code, which on the ER is the only diagnostic a failed transaction returns. The Worker currently cannot distinguish "your phase is wrong" from "file the result first, then retry" — the exact distinction error.rs:205-216 was written to draw.

NOT ON CHAIN, and correctly so: nothing in this review argues for a new stored byte. Finding 1 needs no field (the edge already has both endpoints), finding 2 needs no field (`PIT_BOT` is already generated into map.rs), finding 4 reuses `VOLLEY_INTERVAL_TICKS`, which already exists. `Arena` keeps its 1200 bytes, `Boss` its 50, `LAYOUT_VERSION` stays 1, and no already-live account's zero decodes differently after any of these fixes: `fight_at_tick == 0` still means "no muster scheduled", and `PHASE_MUSTERING = 6` is still unreachable for any account written by the deployed program.

One deployment note that is on-chain and not in my list because the spec already owns it (risk #3): the part-index renumbering permutes `Boss.parts[i]` for any arena caught mid-fight by the redeploy. `reset_for_incarnation` fills every slot from one uniform array, so a LOBBY-phase arena is safe; a FIGHTING one is not. Land it between incarnations. The stale `Boss.y = 320` on such an account is harmless — I measured it, and the fight is still winnable — because `init_arena` and `next_incarnation` both rewrite `Boss.x/y` from `map::BOSS_SPAWN` on the next reset.

## Risks

- Finding 1's fix widens PHASE_EDGES, so the exhaustive 7x7 product test in state.rs:1120 must have its expected count bumped in the same commit or the suite fails for the right reason. The widened edge also re-opens the hazard it was excluded for: a VRF callback landing on an undelegated Arena. That failure is bounded (the oracle retries for the request's 240-slot TTL and then stops) and consume_roll already returns Ok on every rejection path, so it cannot burn the callback into a loop of Errs. Gate the new edge on crank_authority, which tag 12 already does.
- Finding 2's fix changes what move_player accepts, so a deployed app build that lets a lobby player walk north through the gate will start getting BlockedByWall where it used to get Ok. That reads as lag, which is this project's documented misdiagnosis. Program and app ship together, and the client's own walkable check needs the same y > PIT_BOT branch.
- Finding 4's fix means the first volley of a fight arrives 3.2 s later than it does today, which shifts every measured TTK number in spec section 5.4 by one volley. Small, but the table was quoted as measurement.
- I could not measure CU for anything. The spec's own open risk R5 is unresolved and is the trigger condition for finding 1: a crank tick over 399,700 CU ten times deletes the task permanently. Nobody has read 'consumed X of 399700' from a crank log during a 20-seat fight filtered on the arena account. Until that number exists, finding 1's probability is unknown, only its consequence is.
- The two simulations are faithful replays of the shipped Rust logic in Python, not the shipped Rust itself. I matched Rust's truncating-toward-zero integer division explicitly, and the reachability result agrees with the spec's independently-derived section 5.5 shadowing table (mace dominant, thorn2 behind it, core reachable once stripped), which is corroboration rather than proof. The aim set was 960 distinct i8 pairs sampled on a 0.1-degree ring, not all 65,535 pairs.
- I ran no on-chain or ER test. Every finding is traced to shipped source plus a host-side replay; none was reproduced against a validator.
- Finding 6 is reported as a design consequence, not a bug. state.rs:1249 tests the refusal deliberately and the docstrings argue for it. If terminating an arena on any non-WIN outcome is genuinely intended, only the operator runbook needs to say so.
- Per instructions I ran no git command, so I did not verify which commit is actually deployed at JCfWB9zDXYqAv2or2GVriN39enEudWstz3M8sKvVkzc5. The already-live-account analysis assumes the deployed program predates PHASE_MUSTERING and fight_at_tick.
