# recheck:render — adversarial re-review of the shipped client (viewport, rooms, passage, arrows, input, decoders)

## Verdict

The two properties this run was commissioned to prove both HOLD. Viewport containment is proven numerically, not by comment: every walkable unit of every walkable tile in both zone boxes is inside its room (726 arena stands, 1,330 lobby stands, 0 violations), and the fit contains the room at every stage aspect (0.05..6.00 step 0.001 over both rooms, 0 containment failures, 0 aspect mismatches). Each room's content is materialised exactly once across lobby -> gate -> arena, and the renderer/rAF loop/predictor/subscription survive the transition because `#stage` holds a fixed child slot in `<main>`. Decoders are byte-identical to `state.rs`. One writer per node transform everywhere. No listener or rAF leak. The drag provably cannot swallow WASD or Space. BUT the gate beat itself has two real defects: the hold cannot hold (R3 unmounts the local knight one commit before `setHold(true)`, with the veil still at opacity 0), and the room cut is not owned by `cover.finished` (a phase change inside the cover cuts the room early through `Passage`'s else-branch). Both are in the code path the user asked for most, and both are silent. Not shippable as "done" until findings 1 and 2 are closed; everything else is cleanup. tsc re-run this session: app 0, packages/client 0, worker 0.

## New defects

- HIGH — The passage hold is unreachable for the seat it exists for; the local knight vanishes from the waiting room before anything covers it. `Arena.tsx:630` computes `drawOrder = useMemo(() => roomSeats(players.slots, shown), [players, shown])`, and `roomSeats` filters on `s.zone === ZONE_LOBBY` for room A. The payload that flips the local seat to `ZONE_ARENA` therefore drops that seat from `drawOrder` in the SAME commit — `room` is still `'lobby'` because `Passage` has not run its effect yet — so React unmounts the seat `<g>`, `selfRef(null)` fires and `drawn.current = null`. Only afterwards does `Passage`'s passive zone effect call `setBeat`, and only in the NEXT render's layout effect does `setHold(true)` run and the veil start animating — from opacity 0, with `FLAT_LEAD_MS = 115` of delay before the flat veil even begins. So there is a >=115 ms window (long form; 140 ms cover in the live form) in which room A is on screen essentially unveiled with the player's own knight already gone. Everything `Arena.tsx:379-388` and `Passage.tsx`'s header promise — "the knight holds its last drawn position under the opaque veil" — is dead code: `held.current` at `Arena.tsx:529` guards a node that no longer exists, and the correct final placement is actually delivered by `selfRef`'s own `drawn.current = null` + immediate transform write on the room-B mount. This is the same sentence as the last two bug reports ("I cannot see my character"), reintroduced at the one moment the spec spent 536 lines covering. Fix is one predicate: keep the local seat in `drawOrder` while `hold` is set (`roomSeats(...)` plus `s.seat === localSeat && hold`), which makes the documented behaviour real and costs nothing else.
- HIGH — The room cut is not owned by `cover.finished`; a phase change inside the cover cuts the room early. `Passage.tsx:280` lists `phase` and `feedEpoch` in the zone effect's dependency array, and the effect's else branch at `:278` calls `setRoom(roomOf(zone))` unconditionally. Once the beat has opened, `prev.current === zone === ZONE_ARENA`, so ANY re-run of that effect takes the else branch — `passageFires(ARENA, ARENA)` is false — and immediately sets `room = 'arena'`. Concrete trigger, and it is the most common one in the game: the FIRST player through the gate does so in `PHASE_LOBBY`; `App.tsx::useMuster` fires `store.startMatch()` on the same payload that opened the beat, and the resulting LOBBY -> MUSTERING `Arena` notification re-runs the effect. If that lands inside `COVER_MS = 460`, the sequence is: viewBox jumps to `VIEW_ARENA` while `#camera` is still at identity (the `RISE` animation is only created later, in `cover.finished`), so room B appears at its FINAL framing through a veil that is only partway through its `ease-in` fade; then at t=460 `cover.finished` starts `RISE` from `translate(0, -480px)`, so the camera snaps 480 units down and rises back. Net symptom is a visible double-take on the gate transition. Same path fires on a `feedEpoch` bump mid-cover. Fix: skip the else branch while a beat is in flight (`else if (beatRef.current === null) setRoom(...)`), so the only writer of `room` during a beat is the cut.
- MEDIUM — `Shot.tsx` rebuilds its whole 20-seat node pool on every notification, contradicting its own header. `Shot.tsx:590` says "Static from React's point of view: mounted once, never re-rendered into", but the pool at `:593` is a bare `Array.from({ length: MAX_SEATS }, ...)` in the render body with no memo, and `Shot` re-renders whenever `Arena` does — i.e. on every account notification that survives `subscribe.ts`'s dedupe (measured there: 390 of 769 notifications/s are byte-identical and dropped at 20 seats, so ~380/s reach `setWorld` and `World`). Per render that is 13 elements x 20 seats + root = 261 React elements allocated and reconciled, plus all six inline `ref={(el) => void (...)}` closures per seat being fresh identities, so React detaches and re-attaches every one: 120 refs x 2 = 240 ref invocations per render. This is the exact failure mode `Scene.tsx` measured at 11.2 ms/frame and paid to remove, on the layer that sits above the knights. Nothing in the returned tree reads a prop — `MAX_SEATS`, `HEAD`, `SHAFT`, `HEAD_LEN`, `SHAFT_LEN`, `PAL.outline` are all module constants — so `useMemo(() => (...), [])` around the return is a correct one-line fix that also makes the ref identities stable.
- MEDIUM — Two disagreeing rules for R3: `Arena` draws seats by the room on screen, `Shot` draws arrows by the seat's zone. `Arena.tsx:630` filters seats against `shown` (the room `Passage` owns, which lags the chain by the cover on purpose), while `Shot.tsx:391` (`launch`) and `Shot.tsx:510` (`showDamage`) filter against `players.slots[localSeat]?.zone` directly. During the cover the two disagree by construction, so for the whole of `COVER_LIVE_MS = 140` of a mid-fight gate entry the local `zone` already reads `ZONE_ARENA` while room A is still on screen, and every ally arrow and damage number loosed in the pit is drawn at pit coordinates over the waiting room — under a veil that is still fading in. One fact (which room is on screen) stored twice, which is this repo's named signature defect. `Shot` should take the same `room` prop `Arena` already receives rather than re-deriving it.
- LOW — The scene-wide projectile cap is typed twice and the handshake crosses the seam. `Arena.tsx:132 VISIBLE_BULLETS = 32` and `Shot.tsx:237 VISIBLE_PROJECTILES = 32` are the same number with two names in two files, joined only by `budget={shownBullets.length}` -> `cap = Math.max(0, VISIBLE_PROJECTILES - budget)` at `Shot.tsx:528`. Nothing cross-checks them. Concrete failure: set `VISIBLE_BULLETS = 16` to buy frame budget back, run 20 live bullets — `Arena` draws 16, passes `budget = 16`, `Shot` computes `32 - 16 = 16` arrows, and the scene draws 32 projectile nodes again, silently restoring the cap that was just lowered. The measured win the cap exists for (-2.08 ms p50) would be gone with no error anywhere. Move the constant to `sprites.ts` and import it in both (`Arena` already imports `Shot`, so exporting it from `Shot` would be circular).
- LOW — Both room roots are unkeyed `<g>`s at the same JSX slot, so the gate swap is a ~300-node in-place diff rather than an unmount/mount. `Arena.tsx:705` is `{shown === 'lobby' ? WAITING : BOSS_ARENA}`, and both `WAITING` (`WaitingRoom.tsx:586`) and `BOSS_ARENA` (`BossArena.tsx:488`) are `<g>` with no key. React matches by type at the same index, so at the cut it REUSES the DOM `<g>` and walks into it: child 0 `<defs>` vs `<defs>` (LIGHTING) reused, child 1 `<rect class="vp-void">` vs the same reused, child 2 `<g clipPath="url(#waiting-room-clip)">` vs the masonry `<g>` reused and recursively diffed. It happens to be SAFE today — `#gate-portcullis` sits inside `{GATE}` at child index 4 against a `<path>` in `BOSS_ARENA`, so the node `Passage` borrowed and left holding a `fill: 'forwards'` LIFT until its cleanup runs at ~1,100 ms is destroyed rather than repurposed into room B — but that safety is an accident of the two trees' shapes, not a property anything enforces, and it costs a deep diff on the game's most important transition. `key="lobby"` / `key="arena"` is one line and makes both the cost and the safety explicit.
- LOW — `store.ts::setWorld`'s documented invariant is stale: `World` is no longer the only selector returning a whole account. Its comment claims "only a selector returning a whole account re-renders on every frame, and `App`'s `World` is the only one, by design", but `Hud.tsx:260` selects `s.players` and `Hud.tsx:384` / `:449` select `s.boss`. So `PhaseCluster` rebuilds its twenty seat dots (`Array.from({ length: MAX_SEATS })`, ~60 elements) on every `Players` notification, at the same rate as the scene, on the same main thread `controls.ts:381`'s 50 ms pump runs on — which §10.3 identifies as where felt ER lag actually comes from. Select `slots.map(s => s.zone)` shape or a seat count instead, or fix the comment.
- LOW (unverified in a browser) — `DevPanel.useDrag` releases pointer capture unguarded on `pointercancel`. `DevPanel.tsx:251` wires `onPointerCancel: onPointerUp`, and `onPointerUp` at `:233` calls `e.currentTarget.releasePointerCapture(e.pointerId)` with no `hasPointerCapture` guard — where the sibling code in `controls.ts:474` does guard exactly this. Per the Pointer Events spec `releasePointerCapture` throws `NotFoundError` when the pointerId no longer matches an active pointer, which is the state after a cancel; that would throw out of the React handler before `drag.current = null` and before the `localStorage` write, leaving the panel latched mid-drag and the position unsaved. Only Chromium was ever measured on this project and I did not run a browser this session, so the throw is stated from the spec, not observed. The guard is four words and matches the file next door.
