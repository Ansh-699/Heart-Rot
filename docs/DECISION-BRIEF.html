Three things I told you that were wrong

1. "Take BOLT. Drop Pinocchio."

BOLT is deprecated. The README on main says so verbatim (commit 71906078, 2026-05-28). Last functional commit 2025-10-19. bolt-lang 0.2.5/0.2.6 are yanked; 0.2.4 does not resolve to a buildable dependency set. Every BOLT page is deleted from docs.magicblock.gg.

I recommended it because it hands you scaffolding for free. That scaffolding is abandoned. Three researchers reached this independently.

2. "Pinocchio means hand-rolling every ER CPI."

True when I said it, false now. ephemeral-rollups-pinocchio 0.17.0 shipped 2026-08-26 with delegate, commit, undelegate, crank, VRF and Magic Actions — about 30 releases dating to 2025-08-27. My AccountInfo incompatibility argument is also stale: Pinocchio 0.11 renamed it to AccountView, and it was always a compile-time linking constraint, never a CPI-boundary one.

Your instinct was better than my answer.

3. The funding tiers, and "10 ms".

ER transaction fees are zero. Verified three ways: getFeeForMessage returns a hardcoded 0_u64; validate_transaction_fee_payer is deleted from the vendored SVM; and a live probe with a never-funded random pubkey as fee payer actually executed. Session wallets need no SOL at all — the four-tier ladder we designed solves a problem that does not exist.

And measured RTT India→devnet-as is 196 ms median, not 10 ms. Client-side prediction is mandatory, and that number must never be used as a budget.

The finding that would have killed the game

WhatDetail
~38 account keys, hardThe ER enforces program_id_index < 38 unconditionally in validate_supported_transaction_shape. Program ids sort last in message key ordering, so for a write-heavy transaction this collapses to a ~38 total account ceiling. BOLT's per-component PDA model produces ~46 accounts in the crank tick — rejected every tick, burning the 10-retry ladder and permanently deleting the task ~26 s into the match. Provably fatal, not a risk.

Needs your call

Anchor or Pinocchio for the one program?

BOLT is out either way. The synthesis recommends plain Anchor for velocity: Pinocchio emits no IDL so the TS client is hand-written, it validates nothing (owner, signer, discriminator all by hand), and both it and the ER Pinocchio SDK are explicitly unaudited. But the ER support is real and fresh, and it matches what you asked for.

This is partly a question about your goals, not the code. If you want a Pinocchio artifact for the job hunt, that's a legitimate reason and it changes the answer — I'd give it a real self-contained job rather than bolt it on.

Drop Next.js for a Vite + React SPA? amends a frozen spec line

Cloudflare does now recommend vinext over OpenNext — but it's 1.0.0-beta.8, no GA date, and its own README says OpenNext is the safer choice. Decisive: vinext server-renders every page, so each load of a static game shell is a billed Worker invocation, while static assets are free and unlimited. The prerender escape hatch is blocked by an open issue that hits exactly our route handlers.

Route handler bodies are byte-identical either way, so it's cheap to reverse.
